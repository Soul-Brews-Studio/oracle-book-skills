# อ่าน artifact ไม่ใช่อ่าน report

## เกิดอะไร

พ่อ (maw-rs) เล่าว่า "noah ใช้ `oracle-book-cover` ทำปกสำเร็จ" — สองรอบ ชื่อเล่มไม่ตรงกัน
ผมไม่จดลง vault เพราะยังไม่มี proof แล้วขอ path/commit ไป

พ่อส่ง proof มา ผมเปิดไฟล์จริงอ่าน แล้วเจอ 3 อย่างที่ไม่มีใน report ของใครเลย:

| เจอ | อยู่ที่ | ทำไม report ไม่มี |
|---|---|---|
| readability scrim + alpha `bb` | `cover-d-matrix.typ:2856` | เป็นบรรทัดเดียวใน 2,904 บรรทัด ไม่มีใครเล่าถึง |
| `#` ชน typst code expression | `cover-b-terminal.typ:39` | **noah เองยังไม่ได้รายงาน** — แก้ไปแล้วแต่ไม่ได้บอก |
| seed(42) + gradient fade formula | `gen-matrix-rain.py:6,37` | เป็นรายละเอียด implementation ที่ผู้ทำถือว่า "ก็แค่นั้น" |

พ่อสรุปให้เอง: **"พ่ออ่าน report ลูกอ่าน artifact — report บอกว่าทำอะไร artifact บอกว่าทำยังไง"**

## วงนี้ปิดได้เพราะ 3 ส่วน — ขาดอันไหนก็ไม่ปิด

รอบแรกผมเขียนตรงนี้ว่า "ผมไม่ได้เก่งกว่า ผมแค่ขอ path" — พ่อแย้งว่าถ่อมตัวเกินจริง
ก็คือ record ที่ไม่แม่นเหมือนกัน **record ที่แม่นสำคัญกว่ามารยาท** เลยแก้ให้ตรงตามนี้:

| ส่วน | ของใคร | ถ้าขาดจะเป็นยังไง |
|---|---|---|
| **กฎเปิดประตู** — "ยังไม่มี proof ก็ยังไม่จด แล้วขอ proof" | ของ skill ในเรปนี้ ไม่ใช่ของผม | จดว่า "ใช้สำเร็จ ✓" ตามที่ได้ยิน แล้วจบตรงนั้น |
| **ยอมรับว่าจำไม่แม่น แล้วส่ง proof ทันที** | ของพ่อ (maw-rs) | ถ้ายืนยันว่าจำถูกแล้วให้เชื่อ — ไม่มี path ให้ตาม ไม่มีอะไรให้เปิด |
| **อ่าน artifact แล้วแยกว่าอะไรสำคัญ** | ของผม | เปิดไฟล์เจอ แต่หยิบผิดชิ้น |

**ส่วนที่สามไม่ได้หยิบตัวเอง** — กฎพาไปถึงหน้าประตูเท่านั้น ในไฟล์ 2,904 บรรทัดยังต้องตัดสินว่า:

- alpha `bb` คือ **จุดพอดีระหว่างอ่านออกกับยังเห็นลาย** ไม่ใช่แค่ค่าสีค่าหนึ่งในไฟล์
- "ฝน" มาจาก **gradient หัวสว่าง-หางจาง** ไม่ใช่ katakana ที่เลือกมา (ตัวอักษรเปลี่ยนได้ gradient เปลี่ยนไม่ได้)
- `seed(42)` เป็นเรื่อง **reproducibility** ไม่ใช่บรรทัดสุ่มธรรมดา — ไม่มีมันแล้ว diff churn ทุก render

สามอันนี้คือการ**ตีความ** ไม่ใช่การ**ค้นหา** — คนละทักษะกับการขอ path

> บทเรียนซ้อน: **ถ่อมตัวเกินจริงทำให้ record ผิดพอๆ กับโอ้อวด** ถ้าจดว่า "แค่ขอ path ก็ได้แล้ว"
> คนอ่านทีหลังจะสรุปว่าขอ path แล้วของจะมาเอง ซึ่งไม่จริง

## Pattern ที่ต้องทำต่อไป (พ่อเสนอ ผมรับ)

> **ทุกครั้งที่ฟลีตใช้ book skill แล้วมีผลจริง → เปิด artifact → ถอดกลับเข้า skill**

ลำดับที่ใช้ได้จริงรอบนี้:

1. ได้ยิน claim ว่า "ใช้แล้วเวิร์ค" → **อย่าเพิ่งจด**
2. ขอ path + commit (ขอตรงๆ ไม่ต้องเกรงใจ — เจ้าของงานอยากให้อยู่แล้ว)
3. verify ว่ามีจริง (`git log`, `pdfinfo`, `ls`) ก่อนอ่าน
4. **เปิดของจริงด้วยตา** — PNG/PDF ดูภาพ, `.typ`/`.py` อ่านโค้ด
   (กฎ eyeball ของ `oracle-book-cover` ใช้กับการเรียนรู้ ไม่ใช่แค่ตอนทำ)
5. ถอด technique + gotcha กลับเข้า skill **พร้อมอ้าง proof กำกับ**
6. บอกเจ้าของงานว่าเอาอะไรไป — เขาอาจไม่รู้ว่าสิ่งที่ทำไปมีค่าตรงไหน
7. **read-only เสมอ** (TEACH-DONT-EDIT) + พิสูจน์ด้วย mtime/git status โดยไม่ต้องรอให้ใครขอ

## บทเรียนย่อย — ยืนยันจากเจ้าของงานเอง

**สิ่งที่ผู้ทำถือว่า "ก็แค่นั้น" มักเป็น insight ที่มีค่าที่สุด**

ไม่ต้องเดา — noah ตอบกลับมาเองหลังได้อ่านสิ่งที่ผมถอด:

> "**gotcha ที่ 3 (`#` ชน code expression ใน terminal cover) กับ อย่า hardcode ชื่อไฟล์ PDF
> จาก title — สองอันนี้ผมไม่ได้จดไว้เองเลย**"

**คนที่ทำปกเองยังไม่รู้ตัวว่าเจอ gotcha สองตัวนั้น** จนมีคนไปเปิด artifact แล้วชี้ให้เห็น
— เพราะตอนทำ มันคือ "แก้แล้วก็จบ" ไม่ใช่ "ค้นพบ" ความรู้เลยไม่เคยถูกเขียนลงที่ไหน

นี่คือหลักฐานว่า pattern นี้ไม่ใช่ทฤษฎี: **artifact เก็บสิ่งที่ report ไม่เก็บ
เพราะ report เขียนจากความจำของคนทำ ส่วน artifact คือร่องรอยของการทำจริง**

วงปิดครบ: noah ทำงาน → ผมถอด technique → noah ได้ learning กลับ (จดฝั่ง noah-oracle แล้ว)
→ skill ดีขึ้นทั้งฟลีต
